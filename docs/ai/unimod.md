# Unimod-modification-aware peptide sequence parsing

## What this is

`Iso::FromFASTAWithMods` / `parse_fasta_with_mods` (`src/IsoSpec++/fasta_mods.h`/`.cpp`,
C++ core), exposed through `cwrapper.h`/`.cpp` and `IsoSpecPy.ParsePeptideSequence`
(`ParseFASTA` is now a compatibility alias for it), recognizes `[UNIMOD:<id>]` modification
brackets in a peptide sequence and resolves them to atomic composition deltas, in exactly the
notation and placement this monorepo's SAGE fork writes (`crates/sage/src/peptide.rs`):

- N-terminal: `[UNIMOD:<id>]-SEQUENCE`
- Internal: `X[UNIMOD:<id>]` (immediately after the modified residue)
- C-terminal: `SEQUENCE-[UNIMOD:<id>]`

Parsing needs no position-awareness to get this right: a bracket has the same effect (add
that id's composition delta) wherever it appears — the `-` either side of a terminal bracket
is just an ordinary character, silently ignored exactly like any other non-amino-acid byte
always was (see "What changed" below).

## The bug this fixes

Before this feature, the only sequence parser (`parse_fasta`, `fasta.h`/`.cpp`) had no concept
of a bracket at all — every byte, including `[`, `]`, `:`, and digits, went through a fixed
256-entry per-character lookup table, with unrecognized bytes contributing zero and vanishing
silently. That table only knows amino-acid letters, and every letter in the word "UNIMOD" (U,
N, I, M, O, D) happens to be a valid 1-letter amino-acid code — so `[UNIMOD:4]` wasn't ignored,
it was silently misread as six phantom residues (`ParseFASTA('MPEPTC[UNIMOD:4]DEK')` used to
return `C76 H123 N19 O27 S3 Se1`, including a phantom Se from "U", instead of the correct base
composition plus Carbamidomethyl's delta).

## Naming: `fasta` vs `peptide_sequence`

Despite its name, `fasta=`/`ParseFASTA`/`Iso::FromFASTA` has never accepted an actual
FASTA-format file — no `>` header, no multi-record support, no newline handling. It has only
ever accepted a bare peptide sequence string (feeding it a real multi-record FASTA file would
silently miscount the header text as residues too, same class of bug as the bracket one above,
though fixing *that* is out of scope here). `fasta=` is kept as a compatibility alias;
`peptide_sequence=`/`ParsePeptideSequence`/`Iso::FromFASTAWithMods`'s `sequence` parameter is
the honestly-named one and the recommended spelling going forward. Co-author Michał Startek
has completely no idea how things are supposed to be called.

## What changed as a default, and why nothing else did

`ParseFASTA`/`fasta=` now *always* routes through the mods-aware parser, even for a sequence
with no brackets at all — a deliberate, flagged default-behavior change, not an opt-in. A
literal `[` or a bare digit was never valid input before either way, so nothing legitimate
regresses; a sequence with no brackets parses byte-for-byte as before. Every other
previously-tolerated character (spaces, tabs, `*`, a lone `-` not part of a bracket, `X`, `B`,
...) is still silently ignored, preserving the documented "AEDA" == "AE-DA" == "EAXXDA" ==
"AE DA" equivalence (`tests/C++/test_fasta.cpp`'s and this feature's own tests both cover it) —
only `[` became meaningful, and it now must open a well-formed bracket or the call throws.

## The shipped table: what's excluded and why

`data/unimod.csv` (`id,name,mono_mass,composition`) is generated by
`scripts/build_unimod_table.py` from the same source SAGE's own
`crates/sage/scripts/build_unimod_table.py` uses
(<https://www.unimod.org/obo/unimod.obo>) and embedded into the compiled library at build time
as `src/IsoSpec++/unimod_table_data.h` (a checked-in generated header, same "real data as a
literal compiled-in C source file" pattern `element_tables.cpp` already uses — no CMake
codegen step needed). Re-run the script (regenerating both files together) to refresh against
a newer Unimod release.

Only entries IsoSpec can represent correctly as a pure element-count delta are shipped —
**979 of 1560** total Unimod entries with a `delta_composition` field, as of the 2026-09
snapshot this was built against:

- **132 excluded**: isotope-labeled tokens (e.g. `2H(8)`, `13C(3)` — TMT/SILAC-style reagents).
  IsoSpec's periodic table has only natural-abundance elements, no pinned-isotope
  pseudo-elements, so these can't be represented as a simple atom-count delta.
- **449 excluded**: non-element "brick" tokens — Unimod's glycan/derivatization shorthand
  (`Hex`, `HexNAc`, `HexA`, `HexN`, `dHex`, `NeuAc`, `NeuGc`, `Kdn`, `Hep`, `Pent`, `Sulf`,
  `Ac`), each representing a whole monosaccharide/group formula. Each would need its own
  brick→elemental-formula expansion table; not built here.
- **979 shipped**: every remaining entry, including every practically-important common PTM
  (Carbamidomethyl, Oxidation, Phospho, Acetyl, Methyl, GG/ubiquitin, Deamidated) and spanning
  27 distinct elements (not just the amino-acid CHNOSSe set — phosphorylation alone needs P).

Referencing an excluded or genuinely-unknown id is the same error either way — a loud
`std::invalid_argument`/`ValueError`, never a silent misresolution.

## Composition storage: reusing `parse_formula`, not a second tokenizer

Each shipped entry's `delta_composition` is converted, once, at table-generation time, from
Unimod's own notation (`"H(3) C(2) N O"`, space-separated, parenthesized count, count-1
implicit) into IsoSpec's native concatenated formula-string grammar (`"H3C2N1O1"`, signed where
negative, e.g. `"H(-2) O(-1)"` → `"H-2O-1"`) — so loading a table entry's composition is a
literal call to `parse_formula_tokens` (the tokenizing/element-resolution core `parse_formula`
itself now also calls, extracted from `isoSpec++.cpp`), not a second, bespoke parser for
Unimod's own notation.

`parse_formula` itself gained one small, additive extension for this: an element's count may
carry a leading `-` (existing formula strings never contained one, so this changes nothing for
any pre-existing caller).

**Every element's count must be written explicitly in the generated grammar, including implied
count-1** (`"N"` → `"N1"`, never bare `"N"`) — this is load-bearing, not cosmetic:
`parse_formula`'s scanner greedily consumes all consecutive letters as one element name,
bounded on both sides by digits, so a 2-letter symbol (`Cl`, `Ca`, `Co`, `Cr`, `Cu`, ...)
sitting next to a 1-letter one (`C`, `N`, `O`, ...) in the same composition is only unambiguous
because no element's count is ever omitted. `scripts/build_unimod_table.py` enforces this;
`tests/C++/test_unimod.cpp` exercises it against a real shipped composition that mixes both
(`UNIMOD:123`, `ICAT-H` → `H20C15N1O6Cl1`).

## No maps anywhere in this path

Every lookup in this feature is a direct-indexed table, not a `std::map`/`unordered_map`:

- **Unimod id → composition** (`UnimodTable`, `unimod.h`/`.cpp`): a dense `vector<UnimodEntry>`
  indexed straight by id (sized one past the largest shipped id), with a `present` flag —
  `lookup(id)` is a bounds check, not a hash lookup.
- **Element symbol → isotope range** (`element_lookup.h`/`.cpp`): a direct-indexed
  `int[26][27]` table (first letter × optional second letter), built once at static-init from
  `element_tables.h`'s 292 rows — verified those 292 rows resolve to 87 unique symbols with
  zero collisions, so this table has no ambiguity to encode.
- **Override-path "cache"**: not a map either — a single cached `(path, table)` pair
  (`unimod_table_for_path`), since a process realistically uses 0 or 1 distinct override paths
  in its lifetime; a full path-keyed cache would buy nothing. Not synchronized — IsoSpec is
  single-threaded by design (see the top-level `CLAUDE.md`).
- **Per-sequence composition accumulator** (`fasta_mods.cpp`): a fixed-size array, one slot per
  `element_tables.h` row (292), zero-initialized per call — not a string-keyed map.

## The default-vs-override table

`unimod_db_path == NULL`/`None`/`""` (every entry point's default) resolves to
`embedded_unimod_table()` — the compile-time default, parsed once lazily, never re-parsed.
Passing an explicit path loads and parses that CSV (same `id,name,mono_mass,composition`
shape) instead, via `unimod_table_for_path`, cached as described above. This is a per-call
constructor/function parameter everywhere (Python's `unimod_db_path=` kwarg on
`Iso`/`ParsePeptideSequence`/`ParseFASTA`; the C++/C-ABI `unimod_db_path` argument) — not a
process-global flag or environment variable, since this is a library, not a CLI (contrast with
SAGE's own `--unimod-db-path` flag, which doesn't fit here).

## R binding

Unlike the C++/Python surface, R had no existing FASTA/sequence entry point at all before this
feature — `Rinterface.cpp`'s `Rinterface` only ever took a raw atom-count vector plus an
isotope DataFrame. `RParsePeptideSequence` (`src/IsoSpecR/src/Rinterface.cpp`) is a new
`// [[Rcpp::export]]` binding straight to `parse_fasta_with_mods`, mirroring the new C-ABI
functions' shape rather than reusing them (R binds the C++ classes directly, not through
`cwrapper.h`). **Open gap**: this repo has no visible `Makevars`/copy-script showing how
`src/IsoSpec++/*.cpp` reaches `src/IsoSpecR/src/` before `R CMD build` — whoever owns that
out-of-repo step needs to know to also carry over `unimod.cpp`, `fasta_mods.cpp`,
`element_lookup.cpp`, and `unimod_table_data.h`.

## Explicitly out of scope

No glycan/derivatization "brick" support, no isotope-labeled mods, no `[+mass]` numeric-offset
bracket notation (only `[UNIMOD:<id>]`, matching SAGE's own notation exactly), no real
multi-record FASTA-file parsing (`>` headers, multiple records) — both `fasta=`/`ParseFASTA`
and `peptide_sequence=`/`ParsePeptideSequence` continue to accept only a single bare (possibly
bracket-annotated) sequence string.
