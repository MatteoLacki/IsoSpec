# Unimod-modification-aware peptide sequence parsing

## What this is

`Iso::FromFASTAWithMods` / `parse_fasta_with_mods` (`src/IsoSpec++/fasta_mods.h`/`.cpp`,
C++ core), exposed through `cwrapper.h`/`.cpp` and `IsoSpecPy.ParsePeptideSequence`
(`ParseFASTA` is now a compatibility alias for it) and `RParsePeptideSequence`, recognizes
`[UNIMOD:<id>]` modification brackets in a peptide sequence and resolves them to atomic
composition deltas, in exactly the notation and placement this monorepo's SAGE fork writes
(`crates/sage/src/peptide.rs`):

- N-terminal: `[UNIMOD:<id>]-SEQUENCE`
- Internal: `X[UNIMOD:<id>]` (immediately after the modified residue)
- C-terminal: `SEQUENCE-[UNIMOD:<id>]`

Parsing needs no position-awareness to get this right: a bracket has the same effect (add
that id's composition delta) wherever it appears — the `-` either side of a terminal bracket
is just an ordinary character, silently ignored exactly like any other non-amino-acid byte
always was (see "What changed" below).

## The bug this fixes

Before this feature, the only sequence parser (`parse_fasta`, `fasta.h`/`.cpp`) had no concept
of a bracket at all — every byte, including `[`, `]`, `:`, and digits, went through a fixed
256-entry per-character lookup table, with unrecognized bytes contributing zero and vanishing
silently. That table only knows amino-acid letters, and every letter in the word "UNIMOD" (U,
N, I, M, O, D) happens to be a valid 1-letter amino-acid code — so `[UNIMOD:4]` wasn't ignored,
it was silently misread as six phantom residues (`ParseFASTA('MPEPTC[UNIMOD:4]DEK')` used to
return `C76 H123 N19 O27 S3 Se1`, including a phantom Se from "U", instead of the correct base
composition plus Carbamidomethyl's delta).

## Naming: `fasta` vs `peptide_sequence`

Despite its name, `fasta=`/`ParseFASTA`/`Iso::FromFASTA` has never accepted an actual
FASTA-format file — no `>` header, no multi-record support, no newline handling. It has only
ever accepted a bare peptide sequence string (feeding it a real multi-record FASTA file would
silently miscount the header text as residues too, same class of bug as the bracket one above,
though fixing *that* is out of scope here). `fasta=` is kept as a compatibility alias;
`peptide_sequence=`/`ParsePeptideSequence`/`Iso::FromFASTAWithMods`'s `sequence` parameter is
the honestly-named one and the recommended spelling going forward. Co-author Michał Startek
has completely no idea how things are supposed to be called.

## What changed as a default, and why nothing else did

`ParseFASTA`/`fasta=` now *always* routes through the mods-aware parser, even for a sequence
with no brackets at all — a deliberate, flagged default-behavior change, not an opt-in. A
literal `[` or a bare digit was never valid input before either way, so nothing legitimate
regresses; a sequence with no brackets parses byte-for-byte as before. Every other
previously-tolerated character (spaces, tabs, `*`, a lone `-` not part of a bracket, `X`, `B`,
...) is still silently ignored, preserving the documented "AEDA" == "AE-DA" == "EAXXDA" ==
"AE DA" equivalence (`tests/C++/test_fasta.cpp`'s and this feature's own tests both cover it) —
only `[` became meaningful, and it now must open a well-formed bracket or the call throws.

## The shipped table: one CSV, at runtime

`data/unimod.csv` is the single checked-in Unimod table and the only source of modification
data at runtime. Its columns are `id,name,mono_mass,composition,reason`. Original Unimod IDs
are preserved as row indices, gaps and unsupported entries included: an empty `composition`
means "not supported", and `reason` says why. The 2026-09 snapshot has 2148 ID slots and 979
supported compositions.

It is generated by `scripts/build_unimod_table.py` from the same source SAGE's own
`crates/sage/scripts/build_unimod_table.py` uses (<https://www.unimod.org/obo/unimod.obo>);
`--input /path/to/unimod.obo` refreshes from a saved snapshot offline. Re-run it to refresh
against a newer Unimod release.

### Why a runtime CSV and not a compiled-in header

This used to be embedded into the library at build time as a generated
`src/IsoSpec++/unimod_table_data.h` (raw string literal chunks, chunked because a single
~35KB literal tripped MSVC's C2026 "string too big" in CI on windows-11-arm), with a second
generated `unimod_support.h` carrying a `constexpr bool[]` support ledger. Both are gone.
One data file now feeds every binding: no codegen step to keep in sync, no MSVC literal-size
workaround, no possibility of the ledger and the table disagreeing, and `reason` strings
travel with the data instead of as C++ comments nobody can read at runtime. `supports(id)`
on a loaded `UnimodTable` replaces `is_unimod_supported(id)`; it answers the same question
about whatever table the caller actually loaded, rather than about whatever was compiled in.

The cost, paid deliberately: every caller must now supply a table or a path. See
"The default-vs-override table" below.

### What's excluded and why

Only entries IsoSpec can represent correctly as a pure element-count delta carry a
composition — **979 of 1560** entries that have a `delta_composition` field at all:

- **132 excluded**: isotope-labeled tokens (e.g. `2H(8)`, `13C(3)` — TMT/SILAC-style reagents).
  IsoSpec's periodic table has only natural-abundance elements, no pinned-isotope
  pseudo-elements, so these can't be represented as a simple atom-count delta.
- **449 excluded**: non-element "brick" tokens — Unimod's glycan/derivatization shorthand
  (`Hex`, `HexNAc`, `HexA`, `HexN`, `dHex`, `NeuAc`, `NeuGc`, `Kdn`, `Hep`, `Pent`, `Sulf`,
  `Ac`), each representing a whole monosaccharide/group formula. Each would need its own
  brick→elemental-formula expansion table; not built here.
- **979 shipped**: every remaining entry, including every practically-important common PTM
  (Carbamidomethyl, Oxidation, Phospho, Acetyl, Methyl, GG/ubiquitin, Deamidated) and spanning
  27 distinct elements (not just the amino-acid CHNOSSe set — phosphorylation alone needs P).

Referencing an excluded or genuinely-unknown id is the same error either way — a loud
`std::invalid_argument`/`ValueError`, never a silent misresolution. Support in the table is
not a claim that a modification is appropriate at a given site, nor that a particular peptide
has enough atoms for a negative delta.

## Composition storage: reusing `parse_formula`, not a second tokenizer

Each shipped entry's `delta_composition` is converted, once, at table-generation time, from
Unimod's own notation (`"H(3) C(2) N O"`, space-separated, parenthesized count, count-1
implicit) into IsoSpec's native concatenated formula-string grammar (`"H3C2N1O1"`, signed where
negative, e.g. `"H(-2) O(-1)"` → `"H-2O-1"`) — so loading a table entry's composition is a
literal call to `parse_formula_tokens` (the tokenizing/element-resolution core `parse_formula`
itself now also calls, extracted from `isoSpec++.cpp`), not a second, bespoke parser for
Unimod's own notation.

`parse_formula` itself gained one small, additive extension for this: an element's count may
carry a leading `-` (existing formula strings never contained one, so this changes nothing for
any pre-existing caller).

**Every element's count must be written explicitly in the generated grammar, including implied
count-1** (`"N"` → `"N1"`, never bare `"N"`) — this is load-bearing, not cosmetic:
`parse_formula`'s scanner greedily consumes all consecutive letters as one element name,
bounded on both sides by digits, so a 2-letter symbol (`Cl`, `Ca`, `Co`, `Cr`, `Cu`, ...)
sitting next to a 1-letter one (`C`, `N`, `O`, ...) in the same composition is only unambiguous
because no element's count is ever omitted. `scripts/build_unimod_table.py` enforces this;
`tests/C++/test_unimod.cpp` exercises it against a real shipped composition that mixes both
(`UNIMOD:123`, `ICAT-H` → `H20C15N1O6Cl1`).

## CSV quoting

`name` and `reason` are free text and can contain commas (`UNIMOD:0`'s reason, "ontology root,
not a modification", already does), so `split_csv_line` (`unimod.cpp`) handles double-quoted
fields and doubled `""` escapes rather than splitting naively on `,`. One record must occupy
one physical line — the generator writes no embedded newlines and the reader does not
reassemble across lines. A row is accepted with 4 or 5 fields, so a hand-written four-column
`id,name,mono_mass,composition` override CSV (the shape shipped before `reason` existed) still
loads unchanged.

## No maps anywhere in this path

Every lookup in this feature is a direct-indexed table, not a `std::map`/`unordered_map`:

- **Unimod id → composition** (`UnimodTable`, `unimod.h`/`.cpp`): a dense `vector<UnimodEntry>`
  indexed straight by id (sized one past the largest id in the CSV), with a `present` flag —
  `lookup(id)` is a bounds check, not a hash lookup. `lookup`/`supports` take a `uint64_t` and
  bounds-check the full 64-bit value, so an out-of-range id from a sequence cannot wrap into a
  valid index.
- **Element symbol → isotope range** (`element_lookup.h`/`.cpp`): a direct-indexed
  `int[26][27]` table (first letter × optional second letter), built once at static-init from
  `element_tables.h`'s 292 rows — verified those 292 rows resolve to 87 unique symbols with
  zero collisions, so this table has no ambiguity to encode.
- **Path → loaded table**: not a map either — a single cached `(path, table)` pair
  (`unimod_table_for_path`), since a process realistically uses 0 or 1 distinct paths
  in its lifetime; a full path-keyed cache would buy nothing. A caller that genuinely needs
  several tables at once owns `parse_unimod_csv` results directly instead. Not synchronized —
  IsoSpec is single-threaded by design (see the top-level `CLAUDE.md`).
- **Per-sequence composition accumulator** (`fasta_mods.cpp`): a fixed-size array, one slot per
  `element_tables.h` row (292), zero-initialized per call — not a string-keyed map.

## The default-vs-override table

There is no compile-time default table any more, so *something* must name the CSV. Each layer
resolves it at the layer that actually knows where its own data lives:

- **Python**: `_UNIMOD_CSV_PATH` (`IsoSpecPy.py`), module-relative — `IsoSpecPy/data/unimod.csv`,
  which also resolves correctly for an editable install. `unimod_db_path=None`/`""` means
  "the packaged CSV"; any other value is used verbatim. Passed to C++ with `os.fsencode`, so a
  non-ASCII path survives.
- **R**: `system.file("extdata", "unimod.csv", package = "IsoSpecR", mustWork = TRUE)`
  (`Rinterface.cpp`), resolved when `unimod_db_path` is `""`.
- **C++/C ABI**: the caller supplies a `UnimodTable&` or a path. CMake installs the CSV under
  `${CMAKE_INSTALL_DATADIR}/IsoSpec`. A null or empty path with an *annotated* sequence is an
  error ("A Unimod CSV path is required"), not a silent fallback; a sequence with no `[` needs
  no table and is accepted with either. `Iso::FromFASTAWithMods` and `parseFastaWithModsC`
  apply that identical rule (`cwrapper.cpp`'s `resolve_unimod_table` deliberately mirrors
  `fasta_mods.cpp`'s), so the two entry points cannot disagree about what an empty path means.

This is a per-call constructor/function parameter everywhere — not a process-global flag or
environment variable, since this is a library, not a CLI (contrast with SAGE's own
`--unimod-db-path` flag, which doesn't fit here).

## Package resources

`data/unimod.csv` is the canonical file; the two binding-local paths are symlinks to it, so a
checkout has exactly one copy to keep current:

- `src/IsoSpecPy/data/unimod.csv` → `data/unimod.csv`
- `src/IsoSpecR/inst/extdata/unimod.csv` → `data/unimod.csv`

Released archives contain regular files, not links: `skbuild/CMakeLists.txt` installs
`../data/unimod.csv` into the wheel at `IsoSpecPy/data/unimod.csv`, the sdist ships
`/data/unimod.csv` (the symlink is *not* listed separately in `pyproject.toml`, or it would
land as a dereferenced 124KB duplicate), and `R CMD build` dereferences
`inst/extdata/unimod.csv` into the tarball. Nothing is downloaded or generated at install
time.

Because the symlinks are what a checkout relies on, release verification must build the
archives, inspect them, and run the installed packages from *outside* the checkout — a broken
or uncommitted symlink is invisible to an in-tree test run.

## R binding

Unlike the C++/Python surface, R had no existing FASTA/sequence entry point at all before this
feature — `Rinterface.cpp`'s `Rinterface` only ever took a raw atom-count vector plus an
isotope DataFrame. `RParsePeptideSequence` (`src/IsoSpecR/src/Rinterface.cpp`) is a
`// [[Rcpp::export]]` binding straight to `parse_fasta_with_mods`, mirroring the C-ABI
functions' shape rather than reusing them (R binds the C++ classes directly, not through
`cwrapper.h`).

`src/IsoSpecR/src/` reaches `R CMD build` as symlinks into `src/IsoSpec++/`, which the build
dereferences; `unimod.cpp`, `fasta_mods.cpp`, and `element_lookup.cpp` are linked there
alongside the rest. `src/IsoSpecR/src/Makevars` sets `CXX_STD = CXX20` (the core needs C++20
for `<experimental/simd>`), which is why `DESCRIPTION` declares `R (>= 4.0.0)` and
`SystemRequirements: C++20`.

## Explicitly out of scope

No glycan/derivatization "brick" support, no isotope-labeled mods, no `[+mass]` numeric-offset
bracket notation (only `[UNIMOD:<id>]`, matching SAGE's own notation exactly), no real
multi-record FASTA-file parsing (`>` headers, multiple records) — both `fasta=`/`ParseFASTA`
and `peptide_sequence=`/`ParsePeptideSequence` continue to accept only a single bare (possibly
bracket-annotated) sequence string.

## Tests

C++ (`tests/C++/test_unimod.cpp`): known composition deltas for internal/N-terminal/C-terminal
placement, the 2-letter/1-letter element adjacency case, unsupported and unknown ids, malformed
brackets, malformed and out-of-range CSV ids, four- and five-column CSVs, quoted names, path
caching, and the "annotated sequence needs a table" rule. Python (`tests/Python/test_unimod.py`,
`test_unimod_real_data.py`): the packaged CSV's contents and exclusion reasons, overrides
including a non-ASCII path, and a differential run against OldIsoSpecPy over real sequences.
R (`src/IsoSpecR/tests/testthat/test-unimod.R`): the installed resource, its reasons, and
four-column overrides.
